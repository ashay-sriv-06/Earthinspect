17 Claude Code build prompts | Disaster investigations, NASA trends, and traceable adaptation precedents
Prepared 16 November 2026

PRODUCT IN ONE SENTENCE
EarthInspect helps people investigate environmental change, compare lessons from past disasters, and trace every planning lead back to its contextual assumptions, measured findings, and original sources.

This is a complete build sequence, not an addendum to the earlier heat-focused plan. Use this version as the active specification. Preserve useful existing implementation, but reconcile it to this scope. The challenge brief supplied in the conversation is the governing scope; verify submission logistics separately.

THE FOUR CASE FILES
1. Copenhagen, July 2011 cloudburst: urban surface-water flooding and the subsequent Cloudburst Management Plan.
2. Brisbane, January 2011 floods: river and catchment flooding, with official event records and inquiry/response documentation.
3. Camp Fire, California, November 2018: wildfire, evacuation constraints, and NIST's retrospective investigation.
4. Cape Town, 2015–2018 water crisis: multiyear drought context, demand management, and the later municipal Water Strategy. Preserve the distinction between the 2015–2017 drought described in that strategy and the broader crisis period.

The two flood cases demonstrate why a shared disaster label is insufficient for transferring an intervention. The wildfire and drought cases test different mechanisms. A fifth, user-selected place must use the same data and analysis pipeline without adding a city-specific code branch.

THE DEMO'S CENTRAL QUESTION
“What is changing here, which historical experiences are relevant, what makes them transferable or unsuitable, and what additional evidence would change that assessment?”

GLOBAL BUILD CONTRACT
• Preserve a viable existing stack. Greenfield default: React + TypeScript + Vite; FastAPI + Python; SQLite plus an artifact directory; MapLibre GL; a chart library; React Flow only for the focused evidence view. Add deck.gl only for a demonstrated layer need. Avoid introducing a separate graph server or orchestration framework during this sprint.
• Prefer a single deployable container: Python serves the API and built frontend. Use a persistent writable volume for SQLite/artifacts. An ephemeral host must explicitly report its persistence limitation. Do not choose a static-only host for a stateful Python application.
• Four curated cases are source-backed examples. Generalization means the same acquisition, analysis, provenance, and matching functions accept another valid geography. It does not mean globally validated disaster prediction.
• The numerical MVP is NASA POWER regional meteorological context. POWER meteorology is model/reanalysis-derived, not a collection of independent satellite instruments. GIBS provides imagery context. Catalog entries for other missions do not imply implemented numerical adapters.
• The NASA challenge's central output is an interpretable regional time series, estimated rate of change, and explicit statistical uncertainty/significance. A disaster narrative cannot replace this.
• Separate long-term trends, event observations, documented mechanisms, source-reported outcomes, user scenarios, and hypotheses in the database and UI.
• The distinctive feature is evidence-aware transfer: show why a precedent is relevant, what does not match, what is unknown, and how new evidence affects the result. Hypergraph bundles preserve multi-factor context. A graph visualization alone is insufficient.
• Every product button must perform a real action or have a specific disabled reason. No fake activity streams, simulated completed jobs, fabricated statistics, unsupported “AI confidence,” or decorative data.
• Treat fetched documents as untrusted data. Restrict provider hosts; prevent arbitrary server-side URL access. Validate tool arguments, escape rendered content, keep keys server-side, and isolate mutable user sessions. Never log secrets.
• Use meaningful deterministic tests for numerical correctness, provenance, invalidation, and isolation. Keep cosmetic iteration visual. Never expose test fixtures as real environmental evidence.
• Update BUILD_STATE.md after each phase with implemented behavior, acceptance evidence, remaining issues, elapsed time, and next phase. Commit a coherent checkpoint if this is a git repository. Do not modify unrelated work.

PROMPT 06 — DELIVER THE SCIENTIFIC CORE OF THE CHALLENGE
Target: 35 minutes
======================================================================

Build deterministic numerical analysis services independent of the LLM. The default monthly model is an intercept, elapsed time in years, and calendar-month effects. Estimate the linear trend with OLS and heteroskedasticity/autocorrelation-consistent uncertainty using a documented statsmodels implementation. For the MVP, use a predeclared HAC bandwidth of 12 monthly lags and inspect sensitivity at 24. Record all choices. This is an exploratory method, not proof that every time series satisfies its assumptions.

Require at least 120 consecutive valid monthly observations for this inferential path as an explicit product rule, not a universal scientific threshold. If the requested interval has gaps, either ask the user to select a qualifying contiguous interval or return descriptive analysis with a clear limitation. Do not silently compress missing months, zero-fill, or interpolate them for significance testing. Preserve actual elapsed time.

Return slope per decade in the variable's units, 95% confidence interval, p-value, observation count, coverage, period, method/version, uncertainty assumptions, and diagnostics. State “no statistically detectable linear trend under this method” when appropriate, rather than “no change.” For a batch of variables, preserve the full prespecified test family and apply Benjamini–Hochberg adjustment; expose raw p and adjusted q. New exploratory windows start new labeled analyses, not a hunt for the best p-value.

Show raw series, seasonal anomalies with a declared baseline, fitted trend, and method details. Explain confidence intervals as uncertainty about the fitted trend, not future-disaster prediction intervals. Display the actual sign of the result even when it weakens the case narrative.

Add descriptive pairwise associations on aligned overlapping dates. Show both raw correlation and correlation of residuals after removing each variable's fitted trend and seasonal effects. Report overlap and missingness; avoid naive correlation significance claims. Shared model ancestry means these variables are not independent lines of satellite evidence. A lagged association is a hypothesis, not causality or validated forecasting.

Acceptance gate: meaningful synthetic tests recover a known trend with seasonality, reject invalid coverage, preserve calendar spacing, and validate unit conversions. A real case shows its computed slope and interval in the UI with source and method links. Never force a significant result.

PROMPT 08 — IMPLEMENT THE EVIDENCE GRAPH AND REAL HYPEREDGE STRUCTURE
Target: 25 minutes
======================================================================

Implement a persistent typed evidence graph in SQLite using nodes, edges, relationship_bundles, bundle_members, and provenance associations. A separate graph database is unnecessary for this workload. Add schema validation and transactional writes.

Node types should cover Place, Event, Variable, Dataset, Artifact, Analysis, Finding, Source, Intervention, Requirement, Outcome, and Investigation. Use typed directed edges such as DERIVED_FROM, MEASURES, OCCURRED_IN, SUPPORTED_BY, CONTRADICTS, REQUIRES, and SUPERSEDES. Keep names concise and document semantics.

A relationship bundle is a first-class hyperedge with typed member roles. For example, a contextual hypothesis can bind a place, time interval, temperature finding, precipitation finding, proposed mechanism, and supporting publication. Membership alone must not generate causal pairwise edges. A bundle stores its assertion type, evidence status, provenance, time scope, and version. Distinguish measured association from a mechanism described in a source.

Every assertion needs one of: computed finding with artifact/method ancestry; source-reported fact with a locator; explicit analyst assumption; or unverified hypothesis. Preserve event time, source publication time, and ingestion time. Support conflict and supersession without erasing old evidence. Do not attach a made-up probability to an edge.

Implement graph operations the product actually uses: insert an analysis and its provenance; fetch a finding's complete source path; find places with documented shared mechanisms; retrieve interventions whose requirements intersect the target context; retrieve conflicts and unknown prerequisites; and find dependencies of a changed node. Bound traversals and return stable IDs.

Connect completed numerical analyses to graph creation automatically and idempotently. The frontend must read the persisted graph rather than rebuild it from case names.

Acceptance gate: a real analysis becomes graph evidence, a provenance query reaches its immutable artifact and source metadata, repeating ingestion does not duplicate it, and restart preserves the same graph. A multi-member bundle is retrievable with member roles intact.

PROMPT 10 — MAKE CROSS-GRAPH MATCHING EXPLAINABLE AND USEFUL
Target: 25 minutes
======================================================================

Implement a deterministic contextual matching engine between a target investigation's evidence and the solutions graph. This is the central differentiator. It must query persisted graph relationships and requirements, not return a prewritten answer keyed by city.

Represent context with sourced or explicitly user-supplied features: hazard mechanism, geographic scale, relevant environmental findings, time horizon, and intervention prerequisites. Distinguish unknown, compatible, and incompatible. Unknown must never silently equal false or compatible. Do not infer drainage capacity, evacuation capacity, land ownership, water infrastructure, or budget from temperature and rainfall.

Use hard incompatibility rules for genuinely conflicting mechanisms or required conditions. Rank remaining candidates transparently using weighted evidence matches and a separately displayed coverage measure. An ordinal match score is not a probability of success. A candidate with decisive unknown prerequisites should be “needs local evidence,” even if it shares several broad features.

For every candidate return the complete rationale: matched features and evidence IDs; mismatches; unknown prerequisites; source outcome type; applicable spatial scale; reason for inclusion or exclusion; and the next evidence needed. Retrieve negative evidence alongside supportive evidence. Produce at most three useful planning leads with distinct tradeoffs.

Demonstrate why Copenhagen and Brisbane share a flood category but differ in mechanism and scale. Surface-water retention may be a lead for an urban pluvial context; it must not be presented as a complete solution to basin-scale river flooding. If the target context is insufficient, say what must be established first rather than declaring a winner.

Save each match run with graph version, feature inputs, rule version, and candidate IDs. Create candidate bridge edges with hypothesis status. This is transparent candidate-link generation; do not call it a trained link-prediction model.

Acceptance gate: changing a relevant mechanism or prerequisite changes eligibility or the explanation; unrelated changes leave it stable; removing decisive evidence produces an unknown state. Show an actual cross-graph query behind a planning lead.
